## 0. Guerrila doctrine (what changes versus full V6.4)

This checklist is **not** the full-fat V6.4 rollout. It is the early deployment path for the Guerrila profile.

- AF_XDP primary ingress and kernel-bypass discipline
- O(1) money-worker loop
- fixed-layout shared memory and wait-free double-buffer protocol
- `shadow_leader_schedule` for slot-correct venue routing

- No SWQoS relay spend

- No public fallback from private orderflow
- No whale hunting above the Guerrila treasury envelope
- No engineering time spent optimizing lanes that Guerrila forbids using

### 0.3A Optional competition-adjusted strategy mode (approved extension)

- Guerrila MAY run either a `baseline` bank publisher or a `competition_adjusted` bank publisher.
- Both modes MUST collapse into the **same fixed worker-visible bank footprint** already permitted by Guerrila; no new worker-side map, search path, inference path, or dynamic third dimension is allowed.
- `oracle.guerrila.primary_strategy_mode` selects the live publisher: `baseline` or `competition_adjusted`.
- `oracle.guerrila.shadow_strategy_mode` MAY score the non-primary family for counterfactual telemetry, or be `none`.
- `oracle.guerrila.sparse_class_action` controls sparse/stale classes for the adjusted strategy: `fallback_to_baseline` or `drop`.
- Any live promotion of `competition_adjusted` to primary MUST require non-negative shadow uplift versus `baseline` before it becomes the default publisher.

### 0.3B Post-shock SOE / OPSO / Rebalancing extension (observe-first)

- The post-shock mode vocabulary is extended to: `None`, `Backrun`, `Housekeeping`, `Scout`, `Continuation`, `Rebalancing`, `Flatten`, `Drop`.
- Rebalancing is reserved as a fourth post-shock horizon for short-clocked restoration-flow capture, not generic mean reversion; it starts observe-only and may not route live until its own gates pass.
- OPSO (`Optionality-Priced Shock Ownership`) is an oracle / SOE-sidecar layer that prices ownership by subtracting the best admissible fallback value from the current mode value before setting any bid or fee ceiling.
- The worker may consume only fixed-width advisory buckets such as `owner_mode`, `fallback_mode`, `ownership_delta_lcb_bucket`, `bid_ceiling_bucket`, and `kill_mask`; exact quote math, `ShadowGuard`, freshness, inventory, route legality, egress health, and PM release truth remain authoritative.
- OPSO may reduce bids, suppress crowded opportunities, or select a different private-lane owner only inside already-approved route permissions; it may not widen caps, widen route permissions, reopen public execution, or add worker-side auction solving.
- Live OPSO bid shading is disabled until G9B shadow proof shows `tip_saved + fallback_realized_value > missed_backrun_value` on the motifs where shading or skipping would occur.

### 0.5 Recommended rollout philosophy
The spec caps are 10 / 15 / 30 SOL, but the **operational** rollout should still start below them.

Recommended ramp:
1. Observe-only: no sends
2. Tiny live caps: `max_position_per_mint = 1 SOL`, `max_notional_per_entity = 2 SOL`
3. Small live caps: `3 SOL` / `6 SOL`
4. Medium live caps: `5 SOL` / `10 SOL`
5. Pre-spec caps: `10 SOL` / `20 SOL`
6. Full Guerrila caps: `15 SOL` / `30 SOL`

Advance only if the prior rung is profitable, stable, and free of phantom inventory or fee leaks.

## 1. Non-negotiable firewalls (must exist before performance work)

### 1.1 Firewall A - Rust RCU correctness
- payload behind `UnsafeCell<T>`
- volatile payload reads/writes
- `ActiveIdx128B` aligned to 128 bytes
- slot structs aligned to 64 bytes
- `atomic::fence(Ordering::Acquire)` after payload copy
- no plain unsynchronized struct copies on shared hot state

### 1.2 Firewall B - Absolute fee clamp
- clamp `tip_lamports` to the absolute hard ceiling immediately before CU-price conversion
- clamp must be applied to both:
  - public-lane code in the master tree
  - Harmonic lane priority-fee conversion in Guerrila mode

### 1.3 Firewall C - Death Clamp
- if Harmonic egress fails, drop the tx
- never re-route a Harmonic-built signed transaction to public blast

### 1.4 Firewall D - Selective Death Clamp
- `shadow-pm` MUST classify Harmonic failures off the hot path
- class-attributable lethal causes clear only the affected bit in a fixed-width `harmonic_tactic_mask`
- lane-wide Harmonic infrastructure faults or other unlocalizable lethal failures may still flip `harmonic_quarantined = true`
- generic retail-user slippage reverts must release capital and log the error class, but MUST NOT clear unrelated tactic bits or amputate the entire lane

### 1.5 Firewall E - Public-lane amputation
At least one of the following must be true:
- public lane is compiled out behind a feature gate for Guerrila builds, or
- public lane code remains in the tree but runtime config validation makes it impossible to start with a public execution path enabled

The stronger option is feature-gating it out for the Guerrila release artifact.

### 1.6 Firewall F - Harmonic freshness gate
- if `saturating_sub(ingress_record.slot, shadow_health.snapshot_slot) > harmonic_max_state_slot_lag`, the worker MUST strip Harmonic and evaluate Jito instead
- stale Harmonic intents may never be sent just because `ShadowGuard` would later protect principal
- this is a reroute-to-Jito firewall, not a public fallback

### 1.7 Firewall G - Harmonic microscopic CU pad
- Harmonic templates MUST keep a tiny fixed compute pad (`+150 CUs`)
- zero arbitrary padding is forbidden, but so is zero safety margin


### 1.8 Firewall H - ATBA state compression + Jito-only execution
- if a supported CLMM adapter is enabled, workers may receive only a single scalar `dist_to_tick_lamports` (or an equivalently fixed-size sidecar)
- workers must never receive or traverse full tick-array structures
- any ATBA intent is Jito-only; Harmonic is forbidden for this tactic

### 1.9 Firewall I - Clamped apex partials are Jito-only
- a >15 SOL full-curve opportunity may survive only as a ≤15 SOL clamped partial
- any such partial must be explicitly tagged and routed only to Jito
- Harmonic may never carry a clamped apex partial

### 1.10 Firewall J - Obscurity scoring is header-only and bit-packed
- obscurity is derived only from O(1) header-adjacent signals already present in ingress
- deep CPI traversal or variable-time parser walks on AF_XDP are forbidden
- worker consumption must stay fixed-width and L1-resident via a bit-packed bank index, not a third dynamic LUT dimension

### 1.11 Firewall K - Taylor compression is pre-filter only
- Taylor compression may act only as an early-reject gate
- exact integer reserve math, exact `min_out`, exact fee math, and exact `ShadowGuard` bounds remain authoritative
- near-threshold, stale-scalar, or missing-scalar cases must fall through to the exact quote path

### 1.12 Firewall L - Ghost Snipe is cache-prefetch only
- first-fragment logic may prefetch shared pool state into cache
- partial shred/fragment data may never trigger quote, build, sign, or send
- blind-fire Jito bundles from Shred 1 are forbidden

### 1.13 Firewall M - Pre-Sign Egress Admission Gate
- private-lane proxies MUST publish a coarse fixed-width `/dev/shm/shadow_egress_health` sidecar with per-lane health and queue-age classes
- workers MUST consult the chosen private lane before any inventory reservation, envelope build, or signature emission
- lanes marked `down` or severely `degraded` are non-admissible; the alternate private lane may be tried only if all pre-existing route rules for that alternate already pass
- the gate MUST NOT spin, wait, or reopen any public path

### 1.14 Firewall N - Pool-Slot Dominance Gate is thread-local and observe-first
- the gate MUST be strictly thread-local; no shared-memory or cross-worker dominance coordinator is allowed
- the comparison key is fixed-width and limited to substitutive attempts only: `(pool_index, next_scheduled_slot, direction, tactic_family, route_family)`
- suppression is allowed only when the candidate was built from the same `base_state_unix_ns` and does not exceed the incumbent retained LCB by the configured minimum
- initial mode MUST be `observe_only`; live suppression is allowed only after shadow-PnL proof
- if comparison is ambiguous, the candidate MUST pass through

### 1.15 Firewall O - Jito CU density is minimum-empirically-safe only
- Jito CU-density optimization MUST use audited fixed template limits plus the configured tiny empirical pad
- the worker MUST NOT search over CU limits on the hot path
- zero-padding ideology is forbidden, and arbitrary large padding is forbidden
- density telemetry must remain visible separately from gross-tip reporting

### 1.16 Firewall P - Post-trade exhaust scavenging is deterministic Jito-only
- the tactic MUST trigger only when both the upstream competitor-size threshold and the convexity threshold are satisfied
- the tactic MUST bypass front-run evaluation and construct only a deterministic Jito backrun
- Harmonic and public execution are forbidden for this tactic
- actual deployed input MUST remain within the 15 SOL Guerrila corset

### 1.17 Firewall Q - Tick-boundary sabotage is shadow-only
- live trade sizing and live route choice MUST remain unchanged
- the tactic MAY log only `WouldPush_TickBoundary` counterfactuals using the fixed-size CLMM sidecar when available
- correlation with competitor `MissingAccount`-style failures is an observability concern only
- promotion beyond shadow mode requires dedicated replay + observe-only proof and is out of scope for the initial Guerrila live path

### 1.18 Firewall R - Competition-adjusted strategy remains off-path and bank-shaped
- competition density / crowd-heat estimation MUST live entirely off path in `shadow-oracle`
- worker-visible output MUST remain the same fixed bank footprint as baseline publication
- the strategy MAY only lower bid fractions, tighten tactical caps, or drop crowded opportunities
- it MUST NOT widen route permissions, widen the Guerrila treasury corset, or add any new worker-side dynamic selector
- sparse or stale competition estimates MUST obey an explicit fallback policy: `fallback_to_baseline` or `drop`

### 1.19 Firewall S - OPSO and Rebalancing remain sidecar-only, single-owner, and observe-first
- OPSO / SOE scoring MUST live off path in `shadow-oracle` or an equivalent fixed-width sidecar publisher; the money worker MUST NOT solve auctions, run fallback-tree search, or perform sequence/model inference.
- `OpsShockSidecarV1` or any successor sidecar is advisory only: stale or missing sidecar data must fall back to baseline or drop according to config, and it can never legalize a failed exact quote, failed freshness gate, failed `ShadowGuard`, failed inventory fence, or failed pre-sign egress gate.
- PM MUST remain the authority for `mode_owner`, `fallback_mode`, `runner_up_mode`, handoff reason, kill reason, realized markout, and terminal release classification.
- One shock may have only one active owner and one reservation path; OPSO, housekeeping, continuation, Rebalancing, and G9A exhaust scavenging may not double-trigger on the same shock without an explicit PM-owned split rule.
- Rebalancing is observe-only until its own falsification gates prove restoration value after actual route cost; no live Rebalancing route may be enabled by the OPSO sidecar alone.
- OPSO live bid shading is forbidden until shadow replay and observe-only prove positive `ShadingGain`, acceptable `MajorAlphaUnderbidRate`, no public route reopening, no cap widening, no PM ambiguity, and no worker p99 regression.

### 1.20 Firewall T - DPDK remains ingress-only and rollback-safe
- DPDK MAY be evaluated only as an optional post-G12 ingress producer or AF_XDP replacement candidate.
- DPDK MUST emit the same fixed-width `IngressRecord` / feed-ring shape as AF_XDP, or a strictly versioned equivalent that does not redesign the money worker.
- DPDK MAY classify records as private-grade only when the provider feed is proven private-grade; public gRPC / public-geyser records may never be relabeled as DPDK/private to satisfy rollout gates.
- DPDK MUST NOT reopen public execution, public fallback, public QUIC, hot-path RPC, dynamic schema walks, blocking waits, filesystem calls, or socket calls in money workers.
- State freshness, `ShadowGuard`, inventory fence, PM release truth, pre-sign egress admission, cap rung logic, route legality, tip LUT policy, and dominance checks remain authoritative.
- AF_XDP remains the rollback path until DPDK has parity, latency/loss, source-truth, and rollback proof.

### 17B.1 Executive thesis

DPDK is a serious candidate only after the current AF_XDP/private-feed path is proven end-to-end. The upgrade thesis is narrow:

- reduce host-side jitter;
- improve burst tolerance;
- give stronger control over RX queues and DMA rings;
- provide cleaner queue-level drop and timing diagnostics on some hosts.

DPDK does **not** remove network distance, provider feed dependency, state correctness requirements, tip competition, private-lane landing constraints, `ShadowGuard`, inventory truth, or PM release accounting.

| Question | Checklist answer |
|---|---|
| G12 dependency? | No. Finish AF_XDP R0/R1 truth first. |
| Expected benefit | Lower p99/p999 jitter, stronger burst handling, more deterministic RX queue ownership. |
| Main risk | Operational complexity, NIC binding pain, harder tcpdump/debug flow, distraction from EV proof. |
| Correct integration shape | Alternative ingress producer only. Money worker, PM, policy, state, and route logic stay unchanged. |
| Promotion rule | DPDK must beat AF_XDP on measured ingress latency/jitter or packet loss without weakening any Guerrila firewall. |

### 17B.2 Placement in the milestone ladder

| Milestone | DPDK role |
|---|---|
| G12 | Complete current AF_XDP/private-ingress R0 proof, final no-send evidence, micro-market observations, and ShadowGuard ops proof. |
| G13 option A | DPDK feasibility and parity milestone after AF_XDP R1 tiny-live is safe, if AF_XDP jitter/loss is blocking scale. |
| G13 option B | Keep G13 for graduation criteria and move DPDK to G14. |
| Recommended default | Treat DPDK as G14 unless AF_XDP p999 jitter, packet loss, or driver instability blocks scale. |

### 17B.3 Non-negotiable DPDK rules

- [ ] DPDK is not a G12 dependency.
- [ ] DPDK may not reopen public execution or public fallback.
- [ ] DPDK may not relabel public gRPC/geyser data as private-grade ingress.
- [ ] DPDK must emit the same feed-ring record shape or a versioned equivalent consumed without hot-worker redesign.
- [ ] AF_XDP remains the rollback path until DPDK parity and latency/loss proof pass.
- [ ] Source diagnostics must distinguish AF_XDP, DPDK, gRPC/public-geyser, private mempool, Jito searcher, Harmonic searcher, and unknown sources.
- [ ] State freshness, `ShadowGuard`, inventory fence, PM release truth, egress admission, and cap-rung logic remain authoritative.
- [ ] DPDK cannot bypass route legality, tip LUT policy, dominance checks, no-send gates, or live rollout gates.

### 17B.4 AF_XDP vs DPDK vs SmartNIC/FPGA

| Path | Model | Strength | Cost / weakness | Fit |
|---|---|---|---|---|
| AF_XDP | Linux XDP + XSKMAP redirect into UMEM | Good balance of speed and Linux compatibility | Driver/XSKMAP fragility; some Linux abstraction remains | Current target path |
| DPDK | Poll-mode driver owns NIC queues directly in user space | Lower jitter, stronger queue control, mature high-rate packet path | Invasive NIC binding, harder debugging, bigger ops burden | Candidate G13/G14 upgrade |
| SmartNIC/FPGA prefilter | Hardware filters/parses/timestamps and DMA writes compact records | Lowest host CPU overhead and precise timestamps | Expensive, slow iteration, vendor tooling complexity | Later after EV proof |

### 17B.5 Target architecture

The correct DPDK design is a second ingress producer that emits the same feed-ring record shape as the AF_XDP producer. The money worker should not know or care which capture technology produced a valid private-grade record except through diagnostics.

```text
Provider private feed
  -> NIC RX queue
  -> DPDK poll-mode producer
  -> parse/feed-specific reconstruction
  -> existing shadow_feed_ring_w{worker}_p{producer}
  -> existing money worker
  -> existing route/policy/quote/build/no-send/live pipeline
```

Recommended implementation boundary:

- add a `dpdk_producer` module or dedicated `shadow-ingest-dpdk` crate;
- keep route, policy, PM, inventory, `ShadowGuard`, and egress code unchanged;
- keep AF_XDP as primary until parity proof exists;
- run DPDK first as observe-only mirror or separate producer feed ring.

### 17B.6 Source identity and routing semantics

Do not overload diagnostics in a way that hides source truth. Add a new source identity such as `SIGNAL_SOURCE_DPDK_PRIVATE`, or a transport-detail side counter, while mapping both AF_XDP and DPDK private feeds to the same private-grade routing class.

| Source | Classification | Routing posture |
|---|---|---|
| Public gRPC/geyser | Public/fallback | Drop in Guerrila execution posture |
| AF_XDP private feed | Private-grade | May route through approved private lanes |
| DPDK private feed | Private-grade only if provider feed is proven private | May route through approved private lanes |
| Unknown source | Unknown | Fail closed or diagnostic drop |

### 17B.12 Implementation sequence

1. Finish G12 with AF_XDP/private-feed arrival. Do not start DPDK while the NIC is still RX-dark.
2. Capture a baseline AF_XDP timing/loss profile under a known-good private-feed session.
3. Add a DPDK producer behind a feature flag or separate binary. No money-worker changes are allowed except source enum/diagnostics if needed.
4. Implement DPDK EAL init, hugepage check, port/queue setup, RX loop, and clean shutdown.
5. Parse only enough to reproduce the existing AF_XDP producer output. Avoid route/policy logic in the DPDK module.
6. Emit into a separate producer feed ring first. Keep AF_XDP as primary until parity proof exists.
7. Run replay parity using recorded packets before live host tests.
8. Run dual observe-only AF_XDP+DPDK windows and compare records, drops, timing, and worker routing outcomes.
9. Promote DPDK to primary only if it beats AF_XDP on measured p99/p999 or materially reduces loss/jitter.

### 17B.13 Host validation checklist

Run these before any DPDK runtime test.

```bash
# 1. Confirm the feed reaches the NIC before DPDK owns it.
ip -br link
sudo ip link set dev <iface> xdp off || true
sudo ip link set dev <iface> promisc on
sudo timeout 20 tcpdump -ni <iface> -e -vv -c 20 || true
ip -s link show <iface>

# 2. Confirm NUMA and PCI identity.
lspci -nn | grep -i ethernet
cat /sys/class/net/<iface>/device/numa_node
readlink -f /sys/class/net/<iface>/device

# 3. Confirm hugepages.
grep Huge /proc/meminfo
mount | grep hugetlbfs || true

# 4. Confirm driver binding plan before changing it.
ethtool -i <iface>
ip route
ip -br addr
```

### 17B.14 Performance benchmark design

Compare AF_XDP and DPDK under the same feed, same host, same core pinning policy, and same output ring. The benchmark should measure the producer path first and then the end-to-end observe path.

| Benchmark | Measurement |
|---|---|
| Producer-only | NIC RX timestamp to feed-ring write timestamp. |
| Decode path | RX timestamp to decoded `IngressRecord` emission. |
| Worker path | Feed-ring dequeue to route-opportunity/no-send event. |
| End-to-end observe | NIC RX to PM rollout shadow observation. |
| Loss | Provider frame count or packet replay count versus emitted records. |
| Jitter | p50, p90, p99, p999, max, and burst-window loss. |

Acceptance should be based on p99/p999 and loss under burst, not average latency. A DPDK path that is faster at p50 but worse at p999 must not replace AF_XDP.

### 17B.15 SmartNIC / FPGA later-path note

A SmartNIC or FPGA path should not be used for route logic or trading logic. The first useful hardware step is prefiltering and timestamping, not full decision-making.

- Good FPGA target: Ethernet/IP/UDP filter, VLAN filter, feed packet classifier, hardware timestamp, compact DMA record writer.
- Maybe later: simple shred header extraction or fixed metadata extraction.
- Avoid early: full Solana transaction decode, route solving, quote math, signing, PM logic, or dynamic strategy logic in FPGA.
- Promotion condition: only consider after AF_XDP or DPDK has proven positive EV and the team knows exactly which packet fields matter.

### 17B.16 Risk matrix

| Risk | Severity | Mitigation |
|---|---|---|
| Provider feed not arriving | High | DPDK cannot help. Require raw NIC RX proof before any DPDK test. |
| NIC binding breaks management access | Medium | Never bind management NIC. Keep OOB/rollback script. Use dedicated feed NIC only. |
| DPDK distracts from EV proof | High | Gate DPDK behind G12/R1 completion or explicit AF_XDP jitter failure. |
| Diagnostics become ambiguous | Medium | Add distinct DPDK source counters and never relabel public fallback. |
| DPDK faster but less reliable | Medium | Require p999 and loss gates, not p50-only benchmark. |
| State/routing bugs blamed on ingress | Medium | Keep feed-ring format and money-worker path unchanged for parity. |
